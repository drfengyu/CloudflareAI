# 限时活动·翻牌夺宝（v0.15.0）

12 张牌一桌，一局翻开一张。它是幸运转盘的**姊妹玩法**，但赔率口径完全不同：
转盘的返还率要靠蒙特卡洛才知道实际是多少，翻牌的期望是**算出来的精确值**。

- 前台：`/flip`（侧边栏「翻牌夺宝」）
- 后台：系统设置 → 「限时活动（翻牌夺宝）」
- 配置键：`option.flip_config`（一段 JSON，界面按字段拆成数字输入框，管理员不写 JSON）
- 账本：`topup.type = 12`（只有 tcr 奖为正；券奖直接进活动券、不写流水。票价在券兑换 / 礼包时已按 type=15 记过支出，开局不再写负流水）
- 表：`flip_round`（迁移 `migrations/020_flip_round.sql`；`rewardTickets` 列在 `migrations/027_flip_coupon_rewards.sql`）

## 玩法

1. 点「开一局」，按票价折成**整数张**扣当期翻牌活动券（`payWithCoupon`；`roundPriceCredits` 被
   `snapCostToUnit` 吸到券价整数倍），服务端把配置里的 12 个奖项 **Fisher–Yates 洗乱**后写进
   `flip_round.board`，状态 `open`。
2. 牌桌上 12 张牌背面一模一样，点哪张都一样——位置与奖项的对应关系只在库里。
3. 翻开一张即结算，整副牌同时揭晓，状态 `settled`。发奖分两种：面值正好是券单价**整数倍**的奖项
   （`flipRewardTickets`）按整张发**翻牌活动券**；其余奖项的 cr 进**tcr 余额**（tcr，有效期 `rewardValidDays` 天）。
4. 一局只能翻一张。想再翻要再开一局。
5. 中途关页面不丢牌：`findOpenRound` 会把那局 `open` 的牌找回来接着翻，**不会再扣一次票价**。

默认牌桌（`DEFAULT_FLIP_CONFIG.cardRewards`）：

| 档位 | 金额（cr） | 张数 |
| --- | --- | --- |
| 大奖 | 300 / 180 / 120 | 3 |
| 小奖 | 60 / 40 / 20 | 3 |
| 空牌 | 0 | 6 |

票价 100 cr，奖项合计 720 cr → 每局期望 720 ÷ 12 = **60 cr**，返还率 **60%**，站点每局净回收 40 cr。
默认券单价 1 cr，即一局扣 100 张券；券单价只改扣几张券，不改变上面的 cr 期望与返还率。

## 为什么期望是精确值

转盘的内圈落点是加权随机、外圈又是一层加权，实际返还率要跑模拟器才敢报。
翻牌把这件事压平了：**一副牌就是全部样本空间**，每局都从完整的 12 格里等概率取一格，
所以

```text
E[每局返还] = Σ 12 格金额 / 12        （不是「抽多了才准」）
返还率      = E / 票价
```

后台表单实时显示 `奖项合计 / 每局期望 / 返还率 / 每局净回收 / 中奖概率`，改任意一格或票价立刻重算。
`flipExpectation()` 与 `dealFlipBoard()` 在 `lib/flip/config.ts`，纯计算、可在浏览器里跑，
回归测试见 `tests/flip-config.test.ts`（`npx tsx --test tests/flip-config.test.ts`）。

推论：调利润率有两个独立杠杆——**票价**（缩放收入，不动奖池形状）与**牌桌金额**（缩放支出）。
想让返还率随票价联动是不存在的：牌桌是绝对 cr，票价涨一倍返还率就掉一半。

## 券奖：整数倍奖项发活动券

v0.40.0 起，牌桌奖项先按当期券单价判定：`flipRewardTickets(value, unitCredits)` 只在
**面值 = 券单价 × N（N ≥ 1 的整数）** 时返回 N，否则返回 null。

- 是整数倍 → 翻中发 N 张当期翻牌券（`grantCouponToRound`，UPSERT 进 `activity_coupon`），
  **不进 tcr 余额、不写 `topup`**；牌局行 `rewardTickets = N`。
- 不是整数倍（有零头）→ 维持原口径：cr 进tcr 余额，`rewardTickets = NULL`。
- 0 = 空牌，永远不发券也不发钱。

`flip_round.rewardTickets` 记录这一局**实际**发了几张券；NULL 表示发的是 tcr（或还没翻开 / 空牌）。
历史行不需要回填——v0.40.0 之前的奖项全部按 tcr 发放，NULL 正好就是它们的真实口径。
不能靠「金额 ÷ 当前券单价」反推历史，因为券单价与牌桌都可能被改过。

用户侧所有面值展示同一判定：牌桌 12 张牌的卡面、翻开结果、我的牌局「中奖」列与「盈亏」列（券奖按
`实得张数 − 票价张数` 计）、战绩「累计到手 / 最好一张」，凡是整数倍一律显示为活动券图标 × 张数；
战绩汇总的 `won` 只合计 tcr 奖，券奖单列 `wonTickets`；「最好一张」分别聚合 tcr 最好（`best`）
与券奖最好（`bestTickets` + 当时的 `bestTicketCredits`），按实发口径比较、不用 MAX(cr) 反推张数
（历史 tcr 奖可能恰好是券单价的整数倍）。

## 与其他活动的边界

| | 票价支付 | 中奖去向 | 流水 type | 到期过滤 |
| --- | --- | --- | --- | --- |
| 翻牌夺宝 | 按票价扣当期翻牌活动券（整张；不能用其他活动的券或余额） | 整数倍奖发翻牌活动券（无到期）；其余进tcr 余额，`rewardValidDays` 天 | 12（只记 tcr 奖） | `lib/billing/ledger.ts` 把 12 归「活动」类别；正负都按天进账本。中奖发的tcr 余额到期没用完**不记支出**（每日 cron 删行、没有底），落在账本的「与余额差额」里 |

与转盘同一口径：**没有任何倒扣档**，最坏结果是翻到空牌（白花票价），不会扣走已有余额。

## 状态机与无事务写入

D1 走 REST，没有事务，所以每一步都要能「先占住、失败能原路退回」（`lib/flip/store.ts`）：

- `openRound`：窗口与每日上限校验 → `payWithCoupon(票价, 券单价)` → INSERT `flip_round`(`open`, board)。
  建局失败 → 删掉刚建的局 + `refundCouponPayment` 退回原券（不写 12 类流水；
  否则钱包会把正向的 12 类流水当带过期的奖励，到期即隐藏）。
- `flipCard`：读局 → 校验 `status = 'open'` 且属于当前轮次 → **一条带 `status = 'open'` 条件的 UPDATE**
  占住结算（连点与并发重试只有第一个能命中）→ 发tcr 余额 + 正数流水。发奖失败则把这局退回 `open`，
  用户重点那张牌即可，不必重新付票价。
- 结算顺序不能反：先占位再发钱，否则连点能把同一张牌兑两次。

`board` 在翻开之前**绝不进任何响应体**：`findOpenRound` / `openRound` 只返回 `roundId` 与票价，
牌桌随 `revealFlipCard` 的结算结果一起下发。

## 上线步骤

1. 应用迁移（纯增量建表，回退只需 `DROP TABLE flip_round`）：

   ```bash
   node scripts/run-migration.js migrations/020_flip_round.sql
   ```

   2026-11-02 已在线上 D1 执行（`flip_round` 建表 + 两个索引）。

   券奖列（纯增量加可空列，回退只能 `DROP COLUMN`；历史行保持 NULL）：

   ```bash
   node scripts/run-migration.js migrations/027_flip_coupon_rewards.sql
   ```

   必须**先迁移再部署**：drizzle 的 `select()` 会读全部列，活动开着时 `/flip` 与结算路径都会
   扫 `flip_round`，缺列直接 500。

2. 后台 → 系统设置 → 「限时活动（翻牌夺宝）」：勾选开启、填起止时间与票价、按格填 12 张牌的金额。
   开启要求至少一张有奖，否则保存时报错。
3. 关闭活动：取消勾选即可，已翻完的牌局与发放不受影响。
   注意这张卡**只要点保存就会写 `flip_config`**（取消勾选写入的是 `enabled: false`），
   「库里没这个键」只是从没碰过这张卡的状态，不是关掉的开关。

活动未开启或尚未开始时，`/flip` 一条 `flip_round` 查询都不会发（零值直接兜住），
所以代码可以先于迁移部署，不会因为表不存在而让页面报错。
**反过来，先开启活动再补迁移会让 `/flip` 对所有人 500**——2026-11-02 就是这么撞上的，当场补执行迁移后恢复。

## 线上实测（2026-11-02，只用 test@example.com，跑完逐项还原）

开局扣 100 cr → 12 格牌桌落库 → 翻第 7 张实发 30 cr，与库里那副牌的第 7 格一致；中奖进 7 天tcr 余额、
cr 余额不动；`topup` 留下一负一正两条 `type=12`。守卫分支同样实测：没翻完时再点「开一局」复用同一局、
不重复扣款；刷新页面接得上那局；同一局重复提交结算被条件 UPDATE 挡下（零新增流水）；越界位置被拒；
余额不足与每日上限都在扣款前抛出、不留半截局。还原后复验：余额回到 512.9763575601962、
`flip_round` 0 行、`type=12` 流水 0 条、该用户tcr 余额 0 行。

线上现值由管理员自定：窗口 11-02 15:40 ~ 11-13 15:40、票价 100 cr、牌桌合计 1010 cr
（10 张有奖）→ 每局期望 84.17 cr、返还率 84.17%、每日 20 局。

## 已知边界

- 没做管理端牌局页：要看全站的发放与收入，`topup` 里 `type = 12` 的正负数就是全部流水，
  活动页底部的「N 人参与 / 全站 N 局」是即时聚合。若以后要做 `/admin/flip`，按 `/admin/raiden` 的形态抄即可。
- 每日上限（`dailyRounds`）只限**开局**次数，不限翻开；已开局未翻完的牌随时能翻。
- 中途改票价不影响已经开好的局：`flip_round.priceCredits` 在开局那一刻定格。
- 券奖判定也定格在结算时用的 `couponUnitCredits`：同一局开牌与结算之间改券单价，
  按结算那一刻的配置发券；`rewardTickets` 落库后不再受后续配置变更影响。
