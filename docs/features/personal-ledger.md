# 个人账本（`/ledger`）

钱包页原先把「钱怎么变成余额」拆在三张卡里（在线充值订单 / 临时余额明细 / 充值记录），
谁都看不出余额是怎么算出来的。v0.29.0 起账本独立成页，钱包只留余额与最近收支。

## 口径

账目来自两张表：

| 来源 | 算什么 | 为什么必须有 |
| --- | --- | --- |
| `topup` | 所有发放与活动收支，正负都有 | 账本主体（充值、兑换码、签到、返利、任务、赠送、抽奖、雷电、翻牌、站内信、管理员调整） |
| `usage_log.creditsUsed` | API 消费 | 消费只记在用量表，**不进 `topup`**；漏了它就解释不了余额为什么往下掉 |

- 类别划分在 `LEDGER_CATEGORY_TYPES`：充值 `1/2/5/13`、赠送与返利 `3/4/7/8/9/10`、活动 `6/11/12`，
  外加 API 消费。注册奖励（`type=4`）是赠予而不是充值，归「赠送与返利」。
  **新增发放类型必须同时登记 `TOPUP_TYPE_LABEL` 和这张表**，
  漏了不报错，只会被静默算进「活动」——`tests/ledger.test.ts` 会问这一条。
- 日界一律北京墙钟（`strftime('%Y-%m-%d', ts / 1000, 'unixepoch', '+8 hours')`）。
- 金额为 0 的行（既不加钱也不扣钱）不进天表、也不进当天分类；`amount <> 0` 直接写进 SQL，
  不留到 JS 里筛，否则这种行会白占「最近 N 条」的名额并把笔数算多。页面写明不显示。
- 「这天列进表里、点开却一行小计都没有」不能发生：天表与当天小计都用**未取整的原值**判定
  有没有进出（`ledgerHasMovement`，半分以下才算 0），取整只发生在判定之后。
- API 消费按「当天每个模型」聚合成一笔，重度调用用户一天几百次也不会把账本撑爆；
  逐次调用明细仍在 `/history`。

## 临时余额过期为什么没做成第三个来源

发放临时余额时按收入进了 `topup`，到期没用完的部分本该配一笔支出，否则账目合计永远比余额高。
**但这笔支出没有留底**：`vercel.json` 每天 02:00 UTC 跑
`/api/cron/cleanup-expired-balances`，把 `expiresAt <= now` 的 `temporary_balance` 行**整行删掉**，
不写任何流水。

如果账本去读这张表：

- 「过期作废」几乎永远是空的（过期当天到下一次 cron 之间才有几行）；
- 更糟的是**过去某天的账会自己变**——那几小时里查出来的一支出，cron 跑完就没了，
  当天的净收支会跳、甚至整天从表里消失。账本最不能容忍的就是历史会被改写。

所以这一类钱并进下面的差额如实标出。要真正记账，得让清理任务在删行前写一笔负数 `topup`
（并给历史补账），那是动到全体用户账目的写路径，需要单独确认，不在本版。

## 与余额的差额（如实标注，不硬凑）

`当前余额 −（累计收入 − 累计支出）` 在真实库里不为 0，来源三类：

1. 到期作废的临时余额（见上一节，主因）；
2. 早期版本的调用没计量 `creditsUsed`；
3. 管理员直接改余额——下调余额**不写 `topup`**（`app/(dashboard)/admin/users/actions.ts`）。

线上抽样：测试账号差 −310 cr，超管账号差约 −10 亿 cr（历史测试兑换码与手动调整叠加，
无法逐笔还原）。所以账本页单列一行差额并说明来源，**而不是假装合计等于余额**。

差额只在「全部」类别下给出：它是拿账目合计跟**整户余额**对的，筛到某一类时合计天然不等于
余额（筛 API 消费就只剩支出），印出来只会让人以为账本漏了一大笔。筛选态下三项改标
「本类收入 / 本类支出 / 本类净收支」，并写明不与余额对账。

## 交互

- 天表每页 10 天，翻页与类别筛选都走卡片内 server action 局部刷新，不改 URL。
- 点「当天分类」展开该天每个类型的收入 / 支出 / 净收入 / 笔数，末尾一行当天合计；
  类型行与合计行按父表同一套列渲染，数字与父行对齐。
- 换天 / 换筛选会作废在飞的详情请求（响应带序号，对不上就不采纳），否则先点 A 再点 B 时
  A 的小计会画在 B 那一行下面。
- 只看 API 消费时收掉「收入 / 支出」两列（一列恒为 0、一列与净收入重复）。
- 375 窄屏同样只留 日期 / 净收入 / 笔数，表格不出视口。

## 钱包页的「最近收支」

与账本同一份 SQL 口径，但最近几笔只扫**最近 90 天**（`recentWindow()`）：这张卡每次开钱包都要渲染，
不给窗口就等于让重度调用用户的全量 `usage_log` 参与聚合。超过 90 天没动静的账号这里显示
空态，更早的账仍在 `/ledger`（那一页是全量口径，本来就要扫历史算累计）。

「最近 8 笔」只是样本，和余额没有对账关系。钱包页同时用 `listLedgerDays` 算出账本**全量累计**
（与账本页同一把尺子），在卡片底部写明 `余额 = 累计净收支 + 差额`：差额为零就说一致，
不为零就列出三类原因。这样顶部总余额和下方数字能直接对上，而不会把样本合计误当成余额构成。

余额卡里的「永久 / 临时」沿用全站的补正显示口径（永久为负时显示 0，临时显示抵扣后的可用额度）。
欠费抵扣另起一句说明，不再写成「其中 X 已抵扣」——展示的临时额度本身已经扣掉了这部分，
再写「其中」会让人以为还要减一次。

## 为什么走 `d1All` 而不是 drizzle

两表 `UNION ALL` + 多列聚合投影，经 `sqlite-proxy` 会被压成位置数组（`Object.values`），
列名一多极易错位；`lib/db/d1-http.ts` 新增的 `d1All` 直接吃 D1 的对象行按列别名取数，
并且**只接受 SELECT**，非读语句一律抛错。天表与小计的排序仍放 JS 侧：D1 对 `ORDER BY`
聚合别名解析失败（见 `docs/fixes`）；「最近收支」的 `ORDER BY ts DESC LIMIT ?` 排的是子查询
里的普通列，不是聚合别名，已在线上库跑通。

## 已知边界

- 差额行只说明「有多少对不上」，不逐笔还原历史：过期作废与早期未计量消费都没有可回溯的底。
- `topup.createdAt` 在表结构上可空。缺这个时间的行无法归到任何一天，只能落在差额里，
  账本不凭空造一个 1970-01-01。
- 站内信附件发放（`topup type=13`）归入「充值」类别，与兑换码同组。
