# 个人账本（`/ledger`）

钱包页原先把「钱怎么变成余额」拆在三张卡里（在线充值订单 / 临时余额明细 / 充值记录），
谁都看不出余额是怎么算出来的。v0.29.0 起账本独立成页，钱包只留余额与最近收支。

## 口径

账目来自两张表：

| 来源 | 算什么 | 为什么必须有 |
| --- | --- | --- |
| `topup` | 所有发放与活动收支，正负都有 | 账本主体（充值、兑换码、签到、返利、任务、赠送、抽奖、雷电、翻牌、站内信、管理员调整） |
| `usage_log.creditsUsed` | API 消费 | 消费只记在用量表，**不进 `topup`**；漏了它就解释不了余额为什么往下掉 |

- 类别划分在 `LEDGER_CATEGORY_TYPES`：充值 `1/2/5/13`、赠送与返利 `3/4/7/8/9/10`、活动 `6/11/12`、
  过期作废 `14`，外加 API 消费。注册奖励（`type=4`）是赠予而不是充值，归「赠送与返利」。
  过期作废是 cron 补记的真实负数流水，见下文。
  **新增发放类型必须同时登记 `TOPUP_TYPE_LABEL` 和这张表**，
  漏了不报错，只会被静默算进「活动」——`tests/ledger.test.ts` 会问这一条。
- 日界一律北京墙钟（`strftime('%Y-%m-%d', ts / 1000, 'unixepoch', '+8 hours')`）。
- 金额为 0 的行（既不加钱也不扣钱）不进天表、也不进当天分类；`amount <> 0` 直接写进 SQL，
  不留到 JS 里筛，否则这种行会白占「最近 N 条」的名额并把笔数算多。页面写明不显示。
- 「这天列进表里、点开却一行小计都没有」不能发生：天表与当天小计都用**未取整的原值**判定
  有没有进出（`ledgerHasMovement`，半分以下才算 0），取整只发生在判定之后。
- API 消费按「当天每个模型」聚合成一笔，重度调用用户一天几百次也不会把账本撑爆；
  逐次调用明细仍在 `/history`。

## 临时余额过期怎样记账（v0.29.3 起）

发放临时余额时按收入进了 `topup`，到期没用完的部分必须配一笔支出，否则账目合计永远比余额高，
已过期的兑换码就只剩一笔收入。**这笔支出从 v0.29.3 起由清理任务补记**：
`vercel.json` 每天 02:00 UTC 跑 `/api/cron/cleanup-expired-balances`，在删掉
`expiresAt <= now` 的 `temporary_balance` 行之前，按每一行写一笔负数 `topup`：

- `type = 14`（过期作废），`amount = -剩余额度`；
- `id = "expire:<temporary_balance.id>"`，天然幂等，cron 重跑或补跑不会重复记账；
- `createdAt` 用**原到期时间**，账本天表因此在到期那天看到这笔支出，而不是 cron 实际跑的那天。

写入用 `INSERT OR IGNORE`，**先记账、后删行**：记账失败就不删，下一轮重试；
删行只删这一轮选中的 id。消费与回滚路径删临时余额行时**不要**补这类流水——
那些路径的支出已由 `usage_log` 或负数 `topup` 记过，再记一次就是重复扣。
因此这不是 blanket trigger，只有 cron 的「自然过期」这一个入口写 `type=14`。

历史过期行已被旧版 cron 删掉、无法逐笔还原；账本只把这段差额单列说明，不回头读
`temporary_balance`——读它会让过去某天的账随清理自行改写。

## 与余额的对账口径

`当前余额 −（累计收入 − 累计支出）` 非零时如实单列，来源三类：

1. 2026-11-07 前到期作废的临时余额：旧版 cron 直接删行、没有流水（主因，见上一节）；
2. 早期版本的调用没计量 `creditsUsed`；
3. 历史数据里管理员直接改过余额——2026-11-07 前下调余额**不写 `topup`**；现在正负调整都记 `type=2`
   （`app/(dashboard)/admin/users/actions.ts`），此后再有人工改余额会进账本。

线上抽样：测试账号差 −310 cr；超管账号差 −1,000,060,760.90 cr，其中 10 亿来自
2026-06-17 的兑换码 `YDU5QKKA4TWA89XK`（面额 10 亿、余额只有效 7 天，6 月零支出后整笔过期作废），
剩余 −60,760.90 是其他过期临时奖励与未入账的余额变更。

账本「全部」的累计收入 / 累计支出是**原始流水合计**，不再反推、不把差额并入支出。
两类差额都单列在顶部：负差额说明账目比余额多（历史过期或未入账扣减），
正差额说明账外增加的余额变更没进账本。日期为空的脏行也落在这里。
筛选态只看本类原始合计，不与余额对账，三项改标「本类收入 / 本类支出 / 本类净收支」。

「过期作废」筛选和其它类别走同一条路：查天表、可翻页、可展开当天分类
（类型名「过期作废」，只有支出）。

## 交互

- 天表每页 10 天，翻页与类别筛选都走卡片内 server action 局部刷新，不改 URL。
- 点「当天分类」展开该天每个类型的收入 / 支出 / 净收入 / 笔数，末尾一行当天合计；
  类型行与合计行按父表同一套列渲染，数字与父行对齐。
- 换天 / 换筛选会作废在飞的详情请求（响应带序号，对不上就不采纳），否则先点 A 再点 B 时
  A 的小计会画在 B 那一行下面。
- 切到「过期作废」与切到其它类别一致：天表列出每个到期日的作废支出，可翻页、可展开当天分类。
- 只看 API 消费或过期作废时收掉「收入 / 支出」两列（一列恒为 0、一列与净收入重复）。
- 375 窄屏同样只留 日期 / 净收入 / 笔数，表格不出视口。

## 钱包页的「当前余额结算」

钱包不铺原始账，只用**当前结算口径**回答「余额是怎么来的」：

```
有效入账 − 有效支出 = 当前余额 − 历史差额
```

`有效入账` = 账本累计收入 − 真实过期作废支出（`sumExpiredExpense()`，只汇总 `topup type=14` 的负数行）。
同一笔过期金额也从累计支出里剔除：发放是收入、作废是支出，两头抵掉，钱包只回答「还能用的钱怎么进出的」。
没有历史差额时（`gap = 0`）就是 `有效入账 − 有效支出 = 当前余额`。

因此钱包页不会出现已过期的发放金额（例如 10 亿兑换码），也不会把它算成花掉的支出；
账本则把同一笔金额列在到期日的「过期作废」类目里。两边净额一致，
与余额的差只剩历史遗留（`ledgerSettlement().gap`），页面如实标出，不谎称对平。

钱包「最近收支」也排除 `type=14`：过期统一去账本看，结算条已把两头剔掉，
列表里再出现会让人以为重复扣了一次。

## 钱包页的「最近收支」

与账本同一份 SQL 口径，但最近几笔只扫**最近 90 天**（`recentWindow()`）：这张卡每次开钱包都要渲染，
不给窗口就等于让重度调用用户的全量 `usage_log` 参与聚合。超过 90 天没动静的账号这里显示
空态，更早的账仍在 `/ledger`（那一页是全量口径，本来就要扫历史算累计）。

「最近 8 笔」只是样本，和余额没有对账关系，卡片底部明说「不是余额合计」，只给这 90 天窗口的
收入 / 支出 / 净额小计。余额结算在顶部余额卡里，不在这一卡重复。

余额卡里的「永久 / 临时」沿用全站的补正显示口径（永久为负时显示 0，临时显示抵扣后的可用额度）。
欠费抵扣另起一句说明，不再写成「其中 X 已抵扣」——展示的临时额度本身已经扣掉了这部分，
再写「其中」会让人以为还要减一次。

## 为什么走 `d1All` 而不是 drizzle

两表 `UNION ALL` + 多列聚合投影，经 `sqlite-proxy` 会被压成位置数组（`Object.values`），
列名一多极易错位；`lib/db/d1-http.ts` 新增的 `d1All` 直接吃 D1 的对象行按列别名取数，
并且**只接受 SELECT**，非读语句一律抛错。天表与小计的排序仍放 JS 侧：D1 对 `ORDER BY`
聚合别名解析失败（见 `docs/fixes`）；「最近收支」的 `ORDER BY ts DESC LIMIT ?` 排的是子查询
里的普通列，不是聚合别名，已在线上库跑通。

## 已知边界

- 2026-11-07 前过期的临时余额无流水可查，只能以差额形式留在页头；此后的过期逐笔记 `type=14`。
- `topup.createdAt` 在表结构上可空。缺这个时间的行无法归到任何一天，只能落在差额里，
  账本不凭空造一个 1970-01-01。
- 站内信附件发放（`topup type=13`）归入「充值」类别，与兑换码同组。
