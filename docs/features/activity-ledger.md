## 定位

个人账本 `/ledger` 回答「我的余额为什么是这个数」，活动记录回答相反的问题：
**每个限时活动每天给站点带来多少收入、付出多少成本。** 两页共用同一批 `topup` 流水，
但站在站点一侧，正负号与个人账本相反。

- 路由：`/admin/activity`，角色 ≥ 10；导航「管理 → 活动记录」只有这一个入口。
- 旧地址 `/admin/lottery`、`/admin/raiden` 保留为跳转，不再渲染原有明细页。
- 不加新表：全部指标由 `topup` 只读聚合，活动配置、券包与开奖表都不参与。

## 口径

| 方向 | 来源 |
|------|------|
| 站点收入 | `topup.amount < 0`：用户兑换活动券 / 购买珍宝礼包的实付（`type=15`）、转盘倒扣（`type=6` 负数） |
| 站点支出 | `topup.amount > 0`：转盘中奖（6）、雷电奖励（11）、翻牌奖励（12）、每日试炼（17）、灵宠工坊（18）、星匣图鉴（19）、礼包赠送 tcr（16）；`type=15` 的正数按退款计支出 |

- `type=15/16` 是六种活动共用的流水，按描述里的活动名归属（试炼 / 工坊 / 星匣 / 转盘 / 翻牌 / 雷电）；
  识别不到的落在「未归属活动券」，不会凭空消失。
- 金额一律按 cr 面值统计；奖励实际发的是 tcr，到期作废**不回冲**当天支出。
- 礼包让利（`coupon_pack_purchase` 的券面 − 实付）不是现金流水，不计入本表；需要看让利时回
  `/admin/settings` 的礼包配置预览。
- 天表按北京时间（`createdAt + 8h`）切日；不足半分的四舍五入不单独成行。

## 页面结构

- 时间窗：今日 / 近 7 日 / 近 30 日 / 全部，默认近 30 日；窗口按北京日界。
- 概览四格：站点收入、站点支出、净收益（收入 − 支出）、有账天数与流水笔数。
- **各活动本期收支**：按固定顺序列出窗口内每个活动的收入 / 支出 / 净额 / 参与人数 / 笔数；
  没有流水的活动不占行，不在这里补 0 行。
- **天表**：每天一组，第一行是「日期 + 当天合计」，下面按固定顺序列出当天有进出的活动小计
  （每日试炼 / 灵宠工坊 / 星匣图鉴 / 幸运转盘 / 翻牌夺宝 / 雷电行动 / 未归属活动券）；
  每行只给收入、支出、净额、笔数，没有逐笔明细。每页 10 天。
- **用户收支**：一行一个用户（昵称 → 邮箱 → userId 前缀兜底），列出参与过的活动及各自的
  付入 / 领出，再给合计与净额；按「付入 + 领出」倒序，每页 10 人，`upage` 参数独立翻页。
  用户表用 `LEFT JOIN user` 取名，不带出任何联系方式以外的字段。
- 三组数据（天表 / 活动合计 / 用户合计）在同一次页面加载里并行查询，互不依赖。

## 实现注意

- 归属 SQL 与 `activityKeyForRow()` 由同一份 `ACTIVITY_LEDGER_META` 生成，新增活动时只改这一处；
  漏登记的类型不会报错，只会静默落进「未归属活动券」。
- 用户表查询要给 `topup` 起别名 `t`，归属 CASE 用 `attributionCase("t")` 生成；直接字符串替换
  `type` 会误伤活动名里的字符，不要那样写。
- 聚合按 `date + activityKey`、`userId + activityKey` 分组后交给 JS 折叠，D1 不参与排序
  （沿用账本页对 `ORDER BY` 的规避）；用户量按活动参与人数计，不做全站用户扫描。
- 页面只读，没有任何写路径；修改活动配置、发券、发奖都不会经过这里。
