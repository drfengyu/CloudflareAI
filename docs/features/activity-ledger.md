## 定位

个人账本 `/ledger` 回答「我的余额为什么是这个数」，活动记录回答相反的问题：
**每个限时活动给站点带来多少收入、付出多少成本，谁在参与。** 两页共用同一批 `topup` 流水，
但站在站点一侧，正负号与个人账本相反。

- 路由：`/admin/activity`，角色 ≥ 10；导航「管理 → 活动记录」只有这一个入口。
- 旧地址 `/admin/lottery`、`/admin/raiden` 保留为跳转，不再渲染原有明细页。
- 不加新表：全部指标由 `topup` 只读聚合，活动配置、券包与开奖表都不参与。
- 没有全局时间窗。每个活动只展示它实际有流水的时段，时段由首末记账日推导
  （例如「2026-09-23 ~ 2026-11-12」），避免停用的经典玩法被时间窗隐藏。

## 口径

| 方向 | 来源 |
|------|------|
| 站点收入 | `topup.amount < 0`：用户兑换活动券 / 购买珍宝礼包的实付（`type=15`）、转盘倒扣（`type=6` 负数） |
| 站点支出 | `topup.amount > 0`：转盘中奖（6）、雷电奖励（11）、翻牌奖励（12）、每日试炼（17）、灵宠工坊（18）、星图共鸣（19）、礼包赠送 tcr（16）；`type=15` 的正数按退款计支出 |

- `type=15/16` 是六种活动共用的流水，按描述里的活动名归属（试炼 / 工坊 / 星图 / 转盘 / 翻牌 / 雷电；
  星图同时兼容旧名「星匣」）；识别不到的落在「未归属活动券」，不会凭空消失。
- 金额一律按 cr 面值统计；奖励实际发的是 tcr，到期作废**不回冲**当天支出。
- 礼包让利（`coupon_pack_purchase` 的券面 − 实付）不是现金流水，不计入本表；需要看让利时回
  `/admin/settings` 的礼包配置预览。
- 天表按北京时间（`createdAt + 8h`）切日；不足半分的四舍五入不单独成行。
- 全站参与人数按 `userId` 跨活动去重；活动人数是该活动自己的去重人数。

## 页面结构

1. **站点总计**：收入 / 支出 / 净收益 / 参与人数（跨活动去重）四格；
   下方一张「活动 → 活动时段 → 收入 / 支出 / 净额 / 人数 / 笔数」总表。
2. **每个活动一张卡**（每日试炼 / 灵宠工坊 / 星图共鸣 / 幸运转盘 / 翻牌夺宝 / 雷电行动 / 未归属活动券）：
   - 卡头：活动名、活动时段（首末记账日）、收入 / 支出 / 净额 / 人数与笔数。
   - 左栏「按天」：日期倒序的每日收入 / 支出 / 净额 / 笔数，最高 20rem 滚动。
   - 右栏「按用户小计」：一行一个用户（昵称 → 邮箱 → userId 前缀兜底），
     付入 / 领出 / 净额 / 笔数，按「付入 + 领出」倒序，底部一行活动小计。
3. 活动按固定顺序排列；没有流水的活动不出卡。

## 实现注意

- 归属 SQL 与 `activityKeyForRow()` 由同一份 `ACTIVITY_LEDGER_META` 生成，新增活动时只改这一处；
  漏登记的类型不会报错，只会静默落进「未归属活动券」。
- 查询要给 `topup` 起别名 `t`，归属 CASE 用 `attributionCase("t")` 生成；直接字符串替换
  `type` 会误伤活动名里的字符，不要那样写。
- 只有一次数据查询：`GROUP BY activityKey, date, t.userId`，再在 JS 里分别折叠成「按天」与
  「按用户」两份表。D1 不参与排序（沿用账本页对 `ORDER BY` 的规避），排序一律在折叠函数里做。
- 用户表 `LEFT JOIN user` 只取昵称与邮箱；不做全站用户扫描，参与人范围由流水本身限定。
- 页面只读，没有任何写路径；修改活动配置、发券、发奖都不会经过这里。
